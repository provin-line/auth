# Auth — Requirements

> What this repository must provide as part of dPLaaX OSS, derived from the
> dPLaaX Pipeline Protocol.

## 1. Position

This repository provides the **composition-root scaffolds** for the dPLaaX
OSS authentication and authorization stack. It is not an authentication
library; the generated instances compose upstream `@o3co/auth.*` packages
with dPLaaX-specific extensions. Instances are generated per deployment —
see [create-app.md](create-app.md).

| Instance (generated by) | Composes | dPLaaX extension |
|---|---|---|
| `packages/create-auth-provider` | `@o3co/auth-provider-core` + `auth-provider-oauth` + `auth-provider-did` | `DplaaxDidResolver` (did:dplaax) |
| `packages/create-policy-verifier` | `@o3co/auth.policy-verifier.server` + `.builtins` | dPLaaX attribute / rule collectors |

## 2. Mandate from the dPLaaX spec

> **Implementation status (v0.2)**: this section is the **target contract**.
> The shipping default is the bounded `LEGACY_DID_LOGIN@1` grant contract,
> which selects the verification method by controller match (exactly one
> candidate or reject; relationship-blind, and the request's JWS `kid` is
> surfaced but not enforced) and accepts audience-absent requests. The
> strict OWNER profile (exact method-id + three-way `kid` match +
> authentication-relationship binding) is built but not wired into the
> request handler — constructing a provider with an `OWNER_*` contract
> refuses fail-closed; the spec's migration gate
> (`auth.migration.enable-gate`) keeps Fork-Y enrollment disabled
> regardless. The top-level README ("P0 Auth Contract" → "Contract ids")
> and CHANGELOG `[0.2.0]` state exactly what runs today.

### 2.1 Authentication (provider) — Required

- MUST expose an OAuth 2.0 token endpoint that accepts `grant_type=did`.
- MUST resolve `did:dplaax` Owner DIDs by HTTP-fetching `GET {registryBaseUrl}/did/{accountType}/{accountId}/did.json` from the configured DID Registry.
- MUST verify the DID signature challenge against the resolved DID Document's authentication keys.
- MUST issue a JWT asserting the authenticated subject DID. JWT is an **identity assertion only** — see §3.
- MUST reject non-Owner DIDs (Pipeline / Process) at the resolver level. Their signature paths are handled by the Signer API (see provin.oss [docs/protocol/services.md](https://github.com/provin-line/oss/blob/main/docs/protocol/services.md)).
- MUST accept any syntactically valid `accountType` from the parser; allow-list enforcement (`org` only at present) is the DID Registry's responsibility at registration time.
- MUST allow operators to configure `dplaax.registry.allowedRegistries` so DIDs whose `registry` segment differs from the runtime `registryBaseUrl` (migrations, dev/local) remain resolvable.
- MUST operate with file-based / in-memory state only. No database connection.

### 2.2 Authentication (provider) — Out of OSS scope

- DID methods other than `did:dplaax`. The protocol is method-agnostic; the OSS distribution ships only the `did:dplaax` resolver. Adding methods is an extension point.
- Grants other than `grant_type=did`. Upstream `@o3co/auth-provider-oauth` capabilities not wired here are not part of this distribution.
- UI beyond what the OAuth flow strictly requires.
- Automated key sync, key rotation orchestration, fingerprint publishing.

### 2.3 Authorization (policy-verifier) — Required

- MUST expose `POST /verify` returning allow / deny per request.
- MUST register the following dPLaaX attribute collectors:
  - `SubjectDidCollector` — authenticated subject DID
  - `SubjectDidTypeCollector` — DID hierarchy level (owner / pipeline / process)
  - `SubscriberDidCollector` — requesting subscriber DID
- MUST register the following dPLaaX rule collectors:
  - `SubscriberIdentityCheckRuleCollector` — subscriber DID allow-list per `(resource, action)`
  - `SubjectDidTypeRuleCollector` — DID-hierarchy-level restriction per `(resource, action)`
  - `DefaultDenyRuleCollector` — fail-closed default over the declared `(resource, action)` surface
- MUST load policy from YAML. No database.
- **SECURITY NOTE — the PDP is allow-by-default without a declared surface.**
  The upstream evaluator allows a request when zero rules are collected, and
  every other rule collector is dispatch-scoped (it abstains on `(resource,
  action)` pairs it is not configured for). A deployment MUST therefore keep
  `DefaultDenyRuleCollector` enabled with its `surface` listing exactly the
  RPCs the deployment serves (the scaffold ships this; the SoT for the L1
  surface is the `o3co.authz.v1.policy` options in provin.oss
  `api/protobuf/dplaax/*/v1/*.proto`). Removing the collector or emptying its
  surface re-opens the silent-allow hole for unconfigured requests.

### 2.4 Authorization (policy-verifier) — Out of OSS scope

- Provenance Confidence Level evaluation. See the **confidence** entry in provin.oss [docs/GLOSSARY.md](https://github.com/provin-line/oss/blob/main/docs/GLOSSARY.md) and dplaax/spec `rules/confidence.yaml`; receiver-side threshold enforcement is the receiver's responsibility.
- Identity Verification Level evaluation. See the **organization verification** entry in provin.oss [docs/GLOSSARY.md](https://github.com/provin-line/oss/blob/main/docs/GLOSSARY.md); org-domain DNS TXT verification runs outside this service.
- Cross-registry trust scoring, Trust Cluster anchoring, Transparency Log replay.

## 3. Boundary discipline

These rules follow from the dPLaaX responsibility split (authentication =
auth.provider, authorization = each registry's allow-list / policy):

- **JWT is an identity assertion, not an authorization token.** Downstream registries MUST NOT consult JWT scopes for authorization. They consult their own allow-lists.
- **Pipeline Chain connection authentication does NOT go through this provider.** Pipeline Components authenticate peers via direct DID signature verification using the `#auth` verification method (L2 wireauth). See provin.oss [docs/protocol/auth.md](https://github.com/provin-line/oss/blob/main/docs/protocol/auth.md).
- **dPLaaX-specific behavior stays in this repository.** Generalizable improvements are contributed back to upstream `@o3co/auth.*`. Only `did:dplaax` resolver, dPLaaX collectors, and dPLaaX config schema extensions live here.

## 4. Operational requirements

- A fresh `make instances && docker compose up` MUST yield a running provider on `:3000` and policy-verifier on `:3001` with no external dependencies beyond a reachable DID Registry.
- Configuration via HOCON (`application.conf` + `${env}.conf`) using `@o3co/ts.hocon`.
- No database. Persistent state is YAML-backed; transient state may be in-memory.
- Both services start, accept traffic, and respond to `SIGTERM` via graceful shutdown.

## 5. Conformance criteria

A deployment conforms to these requirements if:

1. Provider issues a JWT for a valid `grant_type=did` request signed by an Owner DID.
2. Provider rejects non-Owner DIDs with an explicit error at the resolver.
3. Provider rejects DIDs whose `registry` segment is not in the configured allow-list (which always includes `registryBaseUrl`'s hostname).
4. Provider runs with only YAML config + reachable DID Registry — no DB.
5. Policy-verifier registers the three attribute collectors and two rule collectors listed in §2.3, and accepts YAML policies referencing them.
6. Both services start via `docker compose up` and respond on their configured ports.
